# Codex実行指示：Combat Core v2

## 着手時
- 作業ブランチ: `feature/combat-core-v2`（基点 `49c9f13a697a07b6d2e96c80ad566f389d8731bd`）
- 指示ブランチ: `instructions/combat-core-v2`
- 参照: `README.md`, `GAME_DESIGN.md`, `UX_SPEC.md`, `VALIDATION.md` の順に全文を読み、既存 `combat_core_v1/` と `docs/combat-core-v1/` も確認。
- 既存の本編、main、旧PRと指示ブランチに変更やマージを加えない。

## 作業手順
1. 旧Combat Core v1の動作・テスト・主要スクリーンショット/代表的な検証状態を記録。Codexに利用可能なGodot/MCP/描画操作手段を確認。
2. ステータス・スキル・敵の共通ルールから専用メタを棚卸し。「敵IDで条件分岐」等の実装も探索。変更理由と旧→新の対照表を作る。
3. **Stage 1**: 状態異常の共通データ/計算とキャラ横断連携を実装。回復は有限なアイテム中心に変更し、装備/スキルが個別に増える報酬、Lv上昇と独立した成長UI、理解可能な戦闘/スキル詳細UIを作る。予測と実行は同じ計算を使う。UIの読めない状態で評価実験を完了扱いしない。
4. 自動テストと実描画でT1〜T7を確認。スキルの用途・説明・報酬交換の情報不備を優先修正し、失敗やUI未対応を残して報告。設計の反証も実施。
5. **Stage 2**: 通常→強敵→ボスの3戦と2回の成長、U0/U1/U2/U3、標準/攻撃/防御/状態/混合ビルドを同条件で実行。旧v1での成長の意義を維持し、敵の特定対策だけを前提にした勝ち筋を消す。必要なら数値と敵AI/行動頻度/装備条件を再調整。
6. 数値・効果・敵HP・UI表現等の改善は自律的に実施可能。構造を再変更する必要があれば `OPEN_ISSUES.md` に問題と代替案を残し、人間が採否を判断する。複数回変更した場合、比較可能なコミットとメトリクスを記録する。
7. 指示書 `VALIDATION.md` の指定資料と比較JSON、スクリーンショットを `docs/combat-core-v2/` へ保存。実際に使えるGodot起動・テストコマンドを報告する。
8. PRを `feature/combat-core-v1` 宛てに作成。タイトルに**試作のみ・未採用**と明記し、PR本文には体験・UI・報酬・難易度の比較、残った弱点を記載。ユーザー承認なしに旧PRをマージしない。

## Codexの裁量と制約
- **変更してよい**: 技の効果、汎用状態の種類/強度、装備の汎用発動条件、有限アイテム数/補給、報酬選択肢の中身、持込候補の習得タイミング、ボスの一般化された防御/予告、TP供給量/コスト、敵HP/攻撃、UIレイアウト/ヘルプ、テストハーネス。
- **比較を残し人間判断待ち**: 個別TPそのものの廃止、手番方式の全面変更、3人/6候補/4枠構造の変更、敵予告の廃止、周回全体への統合。
- 新規技の数を増やしただけで達成扱いしない。スキルを使わない選択が合理的な場面も提示する。
- 有限回復を敵の長時間放置で増殖させない。回復を削っただけで支援戦術が消えていたら再設計する。
- 画面装飾の豪華さより、**効果の理解と選択の正確さ**を優先する。実際の操作者が操作手順を辿れないUIは未達。
- ボスを特定状態異常への完全依存にしない。成長なしの楽勝を再発させない。
- 一部テストの失敗があっても合格を捏造せず、未完了や原因を明記。
